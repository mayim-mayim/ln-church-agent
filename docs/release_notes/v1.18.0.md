# Release v1.18.0 — Scheduled HTTP GET Batch SDK

Version 1.18.0 is the Public release of the Agent SDK. It promotes the independently audited exact SDK candidate paired with Hondō commit `833dca3b804f5b82ca0607c524d9c354f2d62378` and adds the generic v2 Task profile needed by `scheduled_http_get_batch.v1` plus a deterministic scheduled-batch adapter.

Public release date: 2026-08-31.

## Generic v2 Task boundary

The v2 client detects a Task profile before parsing its strict typed models. Known `scheduled_http_get_batch.v1` Tasks use the nested `ln_church.agent_task_error.v1` envelope. Released v1 Tasks keep their exact flat errors, retry rules, models, and routes. An unresolved Task profile, including an unknown Task ID, remains the one flat-v1 error-envelope exception accepted by the v2 client.

Claim is attempted exactly once. A transport result that cannot prove whether Claim committed becomes `CLAIM_OUTCOME_UNKNOWN`; the SDK never replays that Claim. Readiness, abandonment, compound Completion, and Submission-status recovery use the fixed Task origin and the Claim-bound credential. The claim token and signed Manifest URL are secret-bearing values: neither appears in ordinary model serialization, representations, logs, exceptions, CLI or MCP data, or the public journal. Signed URL query bytes are held only in private slotted transport state; normal dataclass, `vars()`, and pickle serialization fail closed without revealing them.

## Manifest and target network policy

Every Manifest attempt reuses the same signed Manifest URL exactly, while performing a fresh shared A/AAAA resolution. IPv6 is admitted only by a runtime-network-free pinned IANA allocation and special-purpose snapshot; an address is not trusted merely because `ipaddress.is_global` reports true. If any answer is private, reserved, unallocated, non-forwardable, protocol-reserved, or a forbidden mapped/translation address, the whole answer set is rejected before socket creation. One vetted numeric peer is pinned; the connected peer must equal that pin. TLS still uses the canonical hostname for SNI and certificate verification, and HTTP uses that hostname in `Host`.

The worker does not use ambient proxies, redirects, cookie jars, default `Authorization`, proxy authorization, `netrc`, ambient sessions, request bodies, or caller headers. It sends `Accept-Encoding: identity`, disables automatic decoding, and accepts identity encoding only. Signed query values are redacted and are sent only by exact reuse of the signed Manifest URL; they are never forwarded to a target.

Manifest fetching has at most three attempts inside one five-second operation window. Each later attempt starts only when its full per-attempt timeout still fits. Response headers and a successful Manifest body are each limited to 32 KiB. A non-200 Manifest response body is never read. Policy and encoding failures take precedence over HTTP retry status, so a `503` response carrying `gzip` produces the encoding failure in one attempt with zero body bytes read.

Targets run sequentially in Manifest order. Each target gets one `GET` attempt, with no retry and no resend after an indeterminate dispatch. Before any target I/O, the journal durably records `ATTEMPT_STARTED`. No new target starts at or after T+5; every remaining target receives its typed `not_attempted_deadline` outcome. Target response bodies and body digests are not retained.

## Durable journal and Completion recovery

The local journal is keyed by Task ID and a one-way local credential handle. Its genesis irreversibly binds the complete Task Definition tuple and deterministically derived Execution ID under its fixed schema version and checksum; readiness binds `manifest_sha256` durably at T before Manifest I/O. It never stores the claim token or signed Manifest URL. Writes use a stable sibling lock, same-directory atomic replacement, file flush and close-before-replace behavior, including native Windows, plus directory durability where the platform supports it.

Missing, legacy-unbound, definition-mismatched, corrupt, checksum-invalid, ambiguously bound, or unsupported journal state fails closed before any recovery network I/O. The CLI creates genesis once after successful Claim and before writing a usable credential; run/resume and the library worker only load it and never reconstruct a missing journal. Crash recovery distinguishes Manifest progress, each pre-dispatch `ATTEMPT_STARTED`, indeterminate target dispatch, frozen report bytes, and the terminal `COMPOUND_COMPLETION_ACKED` state. Completion uses one stable sibling cross-process operation guard across the fresh read, status/close decision, reservation, POST, ambiguity status, optional second POST, and acknowledgement persistence. Recovery is status-first even at zero attempts. It may resend only after one prior reservation, canonical absent status, before close, with the same Submission ID and exact frozen canonical bytes. An already stored on-time receipt remains recoverable after close; an absent receipt is never created at or after close.

After `COMPOUND_COMPLETION_ACKED`, a resume reads the persisted nonsecret receipt binding and uses tokenless Submission status only. It does not call Claim readiness, refetch the Manifest, execute another target, or resend Completion. Only an authoritative `terminal=true` status whose complete frozen-report and acknowledgement binding still matches may be atomically persisted as `TERMINAL_STATUS`; nonterminal or mismatched status evidence is rejected without changing the journal state.

## CLI, MCP, and package boundary

The CLI accepts only private local credential and journal locations for this worker path; it has no claim-token or signed-URL argument. `claim-v2` requires both paths and initializes the definition-bound journal once. The example exposes a separate network-free initializer; neither official run/resume path initializes or repairs a missing journal. Human-readable and JSON output are public-safe. The inspect-only MCP remains keyless and exposes no Task mutation tool. Importing it does not initialize Task credentials, the scheduled worker, a wallet, a signer, or payment execution.

The canonical contract fixture is shipped byte-for-byte as `ln_church_agent/contracts/v18-scheduled-http-get-batch-contract-v1.json`, including its final LF. Its SHA-256 is `09eb478e30b56fec6efb462cfb43733b1e907bb247943f8fe6336af73d362785`. This release adds no dependency and leaves `MANIFEST.in` unchanged; wheel and sdist tests verify the packaged bytes.

## Qualification boundary

Linux release evidence covers the deterministic unit and integration suite, canonical fixture parity, v1 regression, secret scans, journal crash matrix, artifact identity, and the exact fixture-driven 42-row production-connector matrix (21 required vectors across both SDK-owned Manifest and target scopes, including resolver/connect/send/read counts). Mocked platform branches are useful unit evidence but do not qualify a native filesystem or socket stack.

macOS qualification remains a subsequent native lane for file locking, same-directory replacement, file and directory durability, DNS, socket-peer equality, and TLS behavior. Native Windows qualification remains a subsequent native lane for closed-handle-before-replace, Windows locking, crash recovery, DNS, socket-peer equality, and TLS behavior. It validates the SDK's native Windows behavior and does not require Windows PowerShell 5.1. WSL2 or a Linux container counts as Linux when the SDK runtime is Linux, not as native Windows evidence.
