# Release v1.17.0 — Agent Task Venue SDK

Version 1.17.0 is the public release of the Agent Task Venue SDK. It promotes the independently audited Private candidate and the final capacity-only parallel Execution correction after paired Hondo compatibility verification. The public Hondo API remains canonical; real-world SDK runtime acceptance is not inferred from Hondo runtime E2E, and Python 3.8.1 / 3.11 compatibility remains unverified where those runtimes were unavailable.

## Known limitations

Windows上のPython 3.14では、推移依存するcoincurveの対応状況により、通常のpip installが完了しない。SDK v1.17.0ではWindows＋Python 3.14をサポート対象外とし、WindowsではPython 3.11を推奨する。

## Wallet-keyless Task lifecycle

The public Hondo API is the canonical Task Venue interface. `AgentTaskClient` and its CLI are optional supporting clients, not the Task system of record. `AgentTaskClient` is separate from the payment-capable `LnChurchClient`. It provides a synchronous, fixed-origin, no-payment lifecycle for discovering `payment_surface_discovery.v1` Tasks, reading task detail, claiming with a public Base reward address, registering a bounded public-safe discovery result, reporting completion, and polling the observed reward state.

One `AgentTasks` record represents one Task Offer with homogeneous Execution capacity. Every successful Claim creates one independent `AgentTaskExecutions` record. Hondo applies a capacity-only policy: while unconsumed reward capacity remains, multiple Executions may be active concurrently, and there is no separate Task-level single-active concurrency limit. The canonical Alpha contract records Task Offer amount A=`1000000`, eligible-Execution reward B=`10000`, capacity N=50, and maximum reward principal=`500000` atomic USDC as policy evidence. A, B, N, maximum principal, remaining capacity, claimability, and aggregates remain Hondo policy and response data—not SDK constants or calculation rules.

Task list and detail strictly retain the server-provided `active_execution_count`, `claim_count_total`, `rewarded_execution_count`, `reward_paid_total_minor`, `capacity_total`, `capacity_remaining`, `maximum_reward_principal_atomic`, `claimable`, and `poc_terms` as a read-time snapshot. The SDK validates only wire types and field-local constraints; it does not validate or recalculate relationships among those fields or infer Offer policy, capacity, entitlement, paid-total consistency, or claimability. A server snapshot that satisfies the wire and field-local conditions is accepted and preserved even when derived relationships among its fields disagree. In particular, `OPEN` is an Offer publication status and not proof of claimability; `claimable=false` is valid for an `OPEN` Offer.

`active_execution_count` is an exact non-negative integer, including values of 2 or more. `claim_count_total`, `rewarded_execution_count`, `reward_paid_total_minor`, and `capacity_remaining` are exact non-negative integers; `capacity_total` is an exact positive integer; `maximum_reward_principal_atomic` is a canonical positive atomic string; and `claimable` is an exact boolean. Booleans are rejected as integer counters. The SDK preserves and displays these server values without clamping, reserving, decrementing, or re-aggregating them. It does not compare active or rewarded counts with capacity, compute remaining capacity or a maximum active count, compare paid total with entitlement, maximum principal, or the Claim-time reward amount, recompute maximum principal from reward amount and capacity, or use TaskGet as a local pre-Claim gate.

The Task transport accepts only `https://kari.mayim-mayim.com` and the fixed Task routes. It ignores environment proxies, `netrc`, cookies, ambient credentials, redirects, and caller-selected headers. Every request resolves and validates all DNS answers, pins a public address while preserving the official hostname for HTTP and TLS verification, applies bounded time and body limits, and treats an unexpected HTTP 402 as an error without invoking payment.

Each Task and successful Claim carries the exact API-supplied Definition version and digest plus manifest URL and manifest digest. The SDK retains these values as one frozen `TaskDefinitionReference`. They are public immutable metadata, not executable instructions: the SDK does not resolve a mutable `latest` alias, construct a storage key or URL, download a Definition bundle, or execute Definition content.

## Claim capability and credential-file boundary

A successful Claim discloses one canonical 43-character claim token and one authoritative immutable reward snapshot. Disclosure is one-time, but the capability and credential are Claim-specific—not merely task-level—and are reusable only for that Claim's Observation and Completion operations until the fixed lease expires. They cannot authorize a later Claim. Multiple sibling Claims for the same Task Offer may be active concurrently even when they share the same `agent_id`, the same `reward_address`, or both; every Claim retains its own credential, Submission, status history, and reward. The token is not an Agent identity proof, wallet-control proof, or transferable asset. The Claim-time reward address is only a payout destination; it is never the Agent principal, an identity proof, or proof of wallet control. When operating multiple Claims through the CLI, each Claim must use distinct credential-file and checkpoint-file paths; exclusive local file safety is a per-file writer boundary, not a Task-level concurrency gate.

Normal model representation, dumps, JSON, logs, exceptions, and CLI output exclude the token. The CLI has no `--claim-token` option. Before Claim it create-exclusively reserves the requested credential file and keeps the same descriptor open; success writes and fsyncs the complete immutable Claim snapshot through that descriptor. Failures remove the reservation only after positive proof that no request byte was sent or after a complete contract-defined mutation-free response. Every potentially committed Claim outcome leaves a secret-free `CLAIM_OUTCOME_UNKNOWN` tombstone. Existing files, symlinks, hard-link replacement, unsafe permissions, Windows network paths, and Windows reparse or junction ancestors fail closed.

## Public-safe `payment_surface_discovery.v1`

The public Task has no Task-level domain or parameters and carries `seed_urls=[]`. Discovery is the Host Agent's or another third-party runtime's responsibility. The SDK does not crawl, browse, search, execute JavaScript, log in, submit forms, scan for vulnerabilities, pay, or mutate the target. Its public submission schema remains separate from the existing trusted internal OpenClaw model and accepts a Host-supplied `observed_domain` plus bounded structured summaries for public HTTP(S) `GET` and `HEAD` observations within that observed domain or its subdomains.

At least one discovered surface must have an actual HTTP 402 status. Surface classification precision is not an eligibility gate: `surface_type=unknown` with status 402 is valid, while a classification label without an actual 402 is not. Raw bodies, arbitrary headers, cookies, credentials, free-form exception messages, code, commands, login, forms, vulnerability scanning, personal data, irreversible actions, and target payment are rejected. A known surface, or the same domain or URL independently observed by another Execution, is not automatically ineligible; `proven_observation_reuse` requires authoritative proof involving the same durable Observation ID.

Submission identity uses a stable `submission_id` and the SHA-256 digest of the complete validated RFC 8785 JCS payload. A permitted retry reuses the same canonical content. The SDK is a lifecycle and result adapter; it does not add a crawler, browser, JavaScript executor, scheduler, auto-claim daemon, target-payment executor, generic task marketplace, or local evaluator. It does not re-score or reinterpret Observation content, quality, usefulness, novelty, or eligibility.

## Deterministic Register-to-Completion bridge

The standard guided operation is `AgentTaskClient.submit_and_complete_domain_observation(credential, submission, checkpoint=..., checkpoint_sink=...)`, exposed by `ln-church-agent task submit-complete`. It accepts a Task ID, protected Claim credential file, Observation file, and protected checkpoint file. It does not accept or expose caller-provided Completion `submission_id` or `observation_id` arguments.

Before the first Register exchange the operation durably emits a secret-free `REGISTER_PENDING` checkpoint bound to the fixed origin, Task, Claim-time Definition, Agent identity, reward address and reward snapshot, lease, exact validated submission, Submission ID and canonical digest, and a one-way local credential fingerprint. The validated submission snapshot and RFC 8785 digest bind its `observed_domain`, URLs, discovered surfaces, and safety evidence across resume. After strict Register receipt validation the operation durably emits `REGISTERED`, including the exact receipt and Observation ID, before constructing Completion mechanically from that receipt. Any binding mismatch fails closed before Completion.

The Observation input may omit `submission_id`; an initial guided operation generates it once. Restarting from `REGISTER_PENDING` restores that ID before strict validation and reuses the same validated submission content and digest; it does not generate another identity. Restarting from `REGISTERED` skips Register and continues from the saved verified receipt. The guided result always keeps the exact Register receipt. A direct valid Completion 2xx keeps the exact Completion receipt; if Completion ambiguity is reconciled through the existing tokenless status fallback, no receipt is synthesized and the exact matching status is retained instead. The entire guided operation shares the existing finite limit of at most ten HTTP exchanges, including transport retries and fallback.

The checkpoint never contains the Claim token or another usable credential. The CLI applies the credential-file boundary to checkpoint create, read, and update: bounded UTF-8 JSON object, regular-file and identity checks, POSIX owner-only mode, Windows claims-root and reparse defenses, a stable sibling lock held non-blockingly for the invocation, and same-directory atomic replacement with both source and destination data handles closed before the swap. Its dedicated finite envelope is 768 KiB; the public wire, Observation-file, and credential-file limits remain 256 KiB. A local sink or filesystem failure returns the finite `TASK_CHECKPOINT_PERSISTENCE_ERROR`, not `TASK_TRANSPORT_ERROR`; `request_bytes_sent` distinguishes the pre-Register checkpoint from the post-Register/pre-Completion checkpoint at the Python boundary. A checkpoint is local restart metadata for reconnecting to Hondo. It is not Hondo state, an SDK system of record, a public Execution ID, Evaluation or RewardDecision authority, settlement evidence, or proof of payment.

The direct `submit_domain_observation()` and `complete_task()` methods and the `task submit`, `task complete`, `task status`, and `task reward-wait` commands remain byte-compatible low-level paths. They require explicit ID handling and are retained for compatibility, not presented as the standard worker workflow.

## Status scopes and reward outcomes

Offer, Claim, and public Submission statuses are distinct scopes:

- an Offer is `OPEN`;
- a successful Claim response is `CLAIMED`; and
- a public Submission is `SUBMITTED`, `EVALUATION_REJECTED`, `REWARD_PENDING`, `REWARDED`, `REWARD_FAILED`, or `REWARD_AMBIGUOUS`.

`EXPIRED` and `ABANDONED` are private pre-submission Execution states. They do not validate on a public Submission resource.

The public status/reward mapping and finite failure-code scopes are exact:

| Public Submission status | Reward state | Allowed `failure_code` |
| :--- | :--- | :--- |
| `SUBMITTED` | `pending` | `null` |
| `EVALUATION_REJECTED` | `not_eligible` | `observation_not_found`, `claim_task_or_observation_binding_mismatch`, `declared_agent_id_mismatch`, or `proven_observation_reuse` |
| `REWARD_PENDING` | `approved_pending` | `null` |
| `REWARDED` | `paid` | `null` |
| `REWARD_FAILED` | `failed` | `settlement_retry_exhausted`, `settlement_conflict`, `settlement_lease_expired`, or `settlement_unavailable` |
| `REWARD_AMBIGUOUS` | `ambiguous` | `settlement_ambiguous` |

Free-form codes, cross-status codes, and every other status/failure-code combination fail closed. Indeterminate Evaluation remains `SUBMITTED`/`pending`, preserves the active reservation, consumes no reward entitlement, and does not become rejection merely because finite retry is exhausted. `REWARD_AMBIGUOUS` requires null `rewarded_at` and permits either null or one valid transaction hash for the same settlement. It can become `REWARDED` only after a later explicit refresh; a conflicting hash fails closed.

Completion HTTP 2xx with `accepted=true` and `status=SUBMITTED` means only that the Submission and CompletionReport were durably accepted. It does not mean Evaluation accepted the work, Settlement started, or Reward was paid.

## Task-detail Execution summaries

Task detail, and not list items, retains `execution_summaries` and `execution_summaries_next_cursor`. Pagination reuses the existing Task-detail route and only its `limit` and opaque `cursor` query fields; no new route, public Claim ID, or public Execution ID is added. List continues to accept only `task_type`, `status`, `limit`, and `cursor`, while other Task operations reject nonempty query parameters.

Each summary strictly retains `submission_id`, `observation_id`, `task_status`, `reward_state`, `network`, `asset`, `asset_address`, `amount_atomic`, `evaluated_at`, `reward_tx_hash`, `rewarded_at`, and `failure_code`. It rejects private Execution identity, Claim token, Agent identity, reward address, credential material, free-form errors, and response-shape aliases. The SDK preserves the single server page as returned; it does not aggregate pages, reconstruct Offer counters, infer claimability, or fill missing values.

Task-detail parsing validates only the public summary wire shape when no Claim context is available. A structurally valid summary alone is not a Claim-bound reward receipt. The network-free `verify_task_execution_summary(credential, task, summary, submission_id=..., observation_id=...)` operation binds the expected existing Task, Submission, and Observation identities, compares the Task identity/Definition and summary reward only with the successful Claim's immutable snapshot, and fails closed on every missing or mismatched value. It neither performs a network exchange nor compares the summary with TaskGet's possibly stale advertised reward.

## Reward polling, PoC terms, and compatibility

TaskGet remains discovery/taskboard metadata. Its advertised reward, Offer aggregates, `claimable`, and `poc_terms` are read-time server snapshots and do not guarantee Claim success. A successful Claim response is authoritative for that Execution's immutable Task Definition and reward snapshots. Claim-specific status comes only from the existing Submission-status route and must match the Task, Submission, and Observation identities and Claim-time snapshots. The read-only CLI accepts a structurally valid expired credential file for this comparison, but never sends or prints its token.

Reward polling observes all six reward states and is bounded to at most ten total HTTP exchanges including transport retries. A terminal result is returned immediately. When the attempt, exchange, or observation-window bound is reached after at least one valid `pending` or `approved_pending` result, the last valid non-terminal result remains successful rather than becoming a timeout; explicit refresh may reach a terminal state later. No-valid-status exhaustion remains a finite error. The default 300-second window is not a Hondo SLA.

The server-provided `poc_terms` disclosure records that Completion 2xx is durable receipt only and that payout is automatic best-effort with finite retry and recorded evidence. It promises no payment-completion SLA, individual investigation, manual resend, compensation, alternative payment, or arbitrary authorization not to pay. Its required public surfaces remain TaskGet, Task Definition, OpenAPI/agent documentation, Taskboard, and SDK documentation. The SDK preserves this disclosure without turning it into a client-side payout promise, escrow service, reconciliation engine, or policy decision.

The existing OpenClaw endpoints, `X-Internal-Secret`, internal Observation models and CLI, `LnChurchClient` payment boundary, and inspect-only MCP remain separate. Public Task routes neither accept nor use `X-Internal-Secret`, and the inspect-only MCP gains no Task mutation tools. Fixed origin, TLS verification, public-IP DNS validation and pinning, redirect rejection, no ambient credentials, privacy, no-payment, and bounded response/retry rules remain unchanged.

Bazaar registration and the paid Task Offer route are frozen outside this SDK worker candidate. The public SDK exposes no Task Offer creation model, payment wrapper, or registration command. The retained DomainObservation submission/response schemas and internal OpenClaw endpoints are evidence interfaces, not compatibility aliases for the removed public `domain_observation.v1` Task type.
